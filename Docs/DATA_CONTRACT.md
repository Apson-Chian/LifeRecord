# 跨端数据契约

状态：**阶段 2 契约与代码回归已落地；不是生产发布许可**。共享样本为 `Tests/Fixtures/data-contract.json`；实际命令/结果见 REPAIR_PROGRESS。C11 的照片引用部分依赖阶段 6，旧客户端仍可发送历史非 UUID ID，不能把兼容入口当成已强制 UUID 的新协议。

## 1. 三类处理边界

| 边界 | 目标 | 禁止行为 |
| --- | --- | --- |
| 新建/主动编辑 | 明确类型、合法范围与枚举，在提交前报具体字段错误 | 把错误值夹紧或填零后悄悄保存 |
| 历史读取 | 保留原始记录，接受已知旧字段缺省；显示投影可以使用有依据的缺省值 | 因新输入范围收紧而丢弃旧值；批量重写 ID/时间/数值 |
| 无法表达的历史记录 | 原始 JSON 与所有未知字段仍可导出；显示具体记录 ID、字段、原因和人工修正方案 | 静默 continue、删除、假装已经同步完整、用当前时间补缺失记录时间 |

历史兼容读取不能直接调用新写入的严格验证器。原始值与展示/统计投影分开；统计不纳入异常值时必须给出可追踪诊断，不能修改原记录。整个批次发生错误时，写入原子性由阶段 3 保障，不能只靠验证器名称承诺。

## 2. 信封、记录类型和 ID

- 继续使用 `meals` / `bodyMetrics` / `workoutEntries` / `settings` / `deletions`。服务端可带 `serverTime`，客户端不能把 serverTime 当成记录版本。
- `favorite`、`exercise`、对话、AI 偏好和 LifeTrack 联动仍为既有本机功能，不因协议契约而删除或擅自上传。
- 新记录使用标准 UUID，传输首选小写；settings 固定 `id="profile"`。图片 ID 继续为 32 个小写十六进制字符。
- 历史非 UUID 的原始 ID 必须保留；不能用新 UUID 替换后冒充同一条记录。iOS 不能表达的 ID 需要只读兼容记录/诊断与原样导出，不允许直接忽略。
- 对同用户、同类型的大小写 UUID 碰撞先只读报告，不自动合并。新写入不得增加大小写别名。对已有大写 ID 的查找/照片绑定应按同一规范匹配，但数据库主键映射变更需另行副本验证。
- 未知顶层和记录扩展字段应保留；手工/AI 修改接口只接收允许编辑的字段，其他字段由已有记录合并保留，不把“字段可透传”等同于“可任意修改”。

是否增加可选 `contractVersion`，以及旧客户端的完整兼容路径，需经共享样本验证后落地。当前没有增加该字段，也没有改变旧请求的含义。

## 3. 时间与通用字段

| 字段 | 新写入规则 | 历史读取/缺省规则 |
| --- | --- | --- |
| id | 非空标准 UUID；settings 除外 | 保留原字符串，碰撞/不可表达 ID 显式诊断 |
| date | 必填有限 JSON number，Unix 秒，0–4102444800 | 不猜缺失日期，不把秒误当毫秒；超范围保留并诊断 |
| updatedAt | 必填有限 number，1–4102444800 | 保留原值；未来时钟冲突由阶段 4 版本设计处理 |
| createdAt | 新餐食必填；有限 Unix 秒 | 旧餐食缺省时，展示投影可用其有效 date；不得覆盖原始导出 |
| note | 字符串，最多 10000 字符，可为空 | 已知旧记录缺省展示为空；数组/对象不能强转成字符串写回 |
| source/inputText/sourceConversationID | 按下表处理 | 缺省与主动清空区别；旧端省略必须保留已有内容 |

JSON bool 不能当数值，数值字符串不属于新写入的 number。NaN/Infinity 禁止进入网络 JSON；解析历史异常应保留可恢复原文并提供诊断。日历日使用设备所选时区；下一日边界用当地下一日 00:00，不能固定加 86400 秒。训练跨午夜仍归开始日。

## 4. 餐食

| 字段 | 新写入规则 | 兼容含义 |
| --- | --- | --- |
| kind | 早餐/午餐/晚餐/加餐 | 旧缺省可展示为加餐，但不能覆盖原始未知值 |
| name | 去外围空白后非空，最多 10000 字符 | 原始文字完整导出；不能用于拼接 HTML 属性 |
| calories | 0–20000 kcal，有限 number | 旧异常保留并提示核对 |
| protein / carbs / fat / fiber | 依次 0–2000 / 0–3000 / 0–2000 / 0–500 g | 旧版缺省可投影为 0；显式 null 或错误类型需要诊断 |
| source | 手动 / AI 估算 | 未知旧来源保留，不假装改成手动 |
| photoIDs | 最多 12 个合法图片 ID | 缺省不得清空已有引用；[] 才表示主动清空列表 |
| inputText | 字符串，允许空 | 缺省保留已有值；"" 表示明确清空 |
| sourceConversationID | 字符串，允许空；非空由客户端产生对话 ID | 不要求其他设备存在本机对话，不因找不到对话删除来源 |

照片上传任务、绑定引用和清理由阶段 6 处理。新契约不能触发历史文件 GC。

## 5. 身体与档案

| 字段 | 新写入统一范围 | 历史处理 |
| --- | --- | --- |
| weight / baselineWeight / targetWeight | 20–400 kg | 旧值不自动夹紧/删除 |
| bodyFat | null 或 1–80 % | 已有 0 等异常仍可读取、导出并诊断，不阻断整批正常记录 |
| waist | null 或 20–300 cm | 未测为 null；省略的旧字段按未测展示，编辑其他字段时保留已有腰围 |
| height | 50–300 cm | 不再以 Android 当前 80–250 阻止读取其他端合法值 |
| weeklyWeightTarget | -5–5 kg/周 | 负数有效；不因数字键盘无法输入负数而改变数值 |
| calorieGoal | 500–10000 kcal | 旧值仍可导出和人工修正 |
| proteinGoal / carbsGoal / fatGoal | 1–600 / 1–1200 / 1–500 g | 不把非法目标变成零；新目标草稿须整体验证后提交 |
| fitnessGoal | 增肌/减脂/维持 | 未知历史值诊断并原样保留 |
| displayName | 字符串，允许空，最多 10000 字符 | 不将昵称作为 AI 指令或 HTML |

这些是输入一致性规则，不代表个体健康建议。settings 必填字段需要完整档案；局部编辑先与当前档案合并再验证，缺失字段不变零、不覆盖其他目标。

## 6. 训练、null、缺省与空数组

- endDate：有限 Unix 秒或 null；新写入 end≥date。进行中用 null；完成统计统一 `date≤endDate≤now`，未来和异常训练保留原始记录并诊断。
- exercises：最多 50 个动作；动作 name 非空且最多 100 字符；bodyPart 为合法部位、未分类或 null；sets 最多 100 组，允许空。
- 每组 reps 为 null 或 1–10000 的整数；weight 为 null 或 0–2000 的有限 number；durationSeconds 为 null 或 1–86400 的整数。0 kg 与未知不同。
- bodyParts：最多 30 个不重复合法部位；每项去外围空白后长度 1–30、无控制字符，不能为“未分类”；允许自定义名称。
- 旧训练省略 bodyParts：读取时从 exercises.bodyPart 推导；只改备注/时间时不得显式写 [] 清空该含义。
- bodyParts=[]：明确没有标签，不应再次 fallback 到动作标签。exercises=[]：明确清空动作。旧端省略这些字段：保留已有字段。
- optional 标量 null 表示明确未填写/清空；缺省表示没发送该字段。非 optional 标量的 null 是校验问题，不擅自换成默认。
- 缺省数组、null 数组、[] 不得混成一个状态；已有服务接受的 null 行为必须经旧客户端样本确认后决定兼容投影，不批改历史值。

## 7. 删除、版本与只读诊断

- tombstone 保留 `{id, recordType, deletedAt}`，recordType 仍为 meal/body/workout；不因为当前设备没有对应记录就丢弃。
- 删除与修改的胜负留待阶段 4 的统一设计与收敛测试；本阶段不决定永久删除优先，不清空/按年龄淘汰 tombstone。
- 只读诊断应包含用户可识别的原记录类型/ID、字段路径、原因与原始内容导出入口；按用户隔离，不能包含 API Key 或同步密钥。
- 人工修正必须引用原 ID 和当前版本，预览变更并保留未修改字段；不自动生成“修正版新记录”替代旧记录。

## 9. 本阶段实际兼容行为

- 后端只对新建/发生变化的记录执行新写入校验；原样历史重放和过期快照不改写字段。部分字段省略与未知扩展由原记录合并保留。新同步输入必须有有效 date，已有记录的部分旧端编辑可沿用其既存 date。
- Swift 缺省旧餐食字段仅用于显示投影；未修改版本在出站时重用原始 wire 数据，不把默认值、随机动作 ID 或缺省数组写回。每次有效入站响应存放于应用私有、按账号摘要区分的诊断文件；导出包含 `compatibilitySnapshot`。该 JSON 包含敏感健康数据，应按普通导出保管，不包含凭据。
- 无法解码、非 UUID 和大小写碰撞的 iOS 记录保留在原始快照，显式报告，其他可表示记录继续同步；不创建替代 ID。Android 保留原始 JSONObject，历史读取不使用新输入数值范围；错误类型仍明确报错。
- `GET /liferecord-api/diagnostics` 需认证，只返回当前账号的只读诊断与原始快照。人工修正先导出，再按原 ID/当前版本使用已有编辑接口预览；大小写碰撞暂不自动合并。不能将诊断导出盲目作为写请求重放。
- UUID 别名只在同账号/同类型且恰有一个既存匹配时解析到其原 ID，不批改数据库主键。已存在多个别名时拒绝修改并要求人工核对。新客户端继续创建 UUID；旧非 UUID 记录仍原样可导出。
- 照片历史归属/大小写引用台账及多记录共享引用尚待阶段 6；本阶段没有照片清理或历史 ID 迁移。删除冲突、版本与幂等尚待阶段 4。
